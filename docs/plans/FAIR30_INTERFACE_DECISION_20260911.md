# Fair30之后：任务接口复核与研究去留

> 后续执行完成：120逻辑单元、124请求、171测试及独立回放通过。澄清后证据无净任务收益，停止当前实现扩量。见[真实结果](../experiments/scene_pilot12/INTERFACE_DIAGNOSTIC_RESULTS_20260911.md)。以下保留采集前设计。


本文件是实验设计决策，不是论文正文。2026-09-11，完成离线审计；本次API调用0，旧实验分数不变。

## 1. 结论先行

**当前保留“模型抽取规则＋确定性执行器”作为工程基线，暂停把计算事实复核作为核心创新。** 暂不把接口改成直接输出路线来挽救旧结果。先用一个严格隔离的接口诊断，判断原句中的职责冲突是否解释了合同失败；即使修复有效，也只能算接口改进，不能自动升级为DARC方法贡献。

Fair30的官方结果仍是Direct56/60、语言复核59/60、证据复核57/60；证据原始任务成功48/60，12次合同失败。这一结论既不应被粉饰，也不能扩大为“计算事实对所有规划问题无用”。

## 2. 离线审计新增发现

证据组的12次合同失败中，5次在selection填药房ID，6次填INFEASIBLE，1次有多段输出。对前11条只作“其填入的决策是否与gold相符”的辅助检查：

| 类型 | 数量 | 决策内容与参考答案一致 | 不一致 |
|---|---:|---:|---:|
| 药房ID写入规则字段 | 5 | 4 | 1（F07第二次） |
| INFEASIBLE写入规则字段 | 6 | 5 | 1（F25第一次） |
| 非单个JSON对象 | 1 | 不作宽松提取 | 不作评分 |

9条含正确决策内容，但仍违反原先约定的规则输出合同，**全部保留原SCHEMA_FAILED**。这项检查只用于定位错误层次，不能将证据组改报57/60原始成功，也不能混合规则输出与直接决策输出生成新排行榜。未核验这些回答的每句解释都正确，部分规则字段也仍有误。

可复现诊断：`9-AutoDriving-core/data/fair30_interface_diagnostic_v1/failure_diagnosis.json`。

## 3. 方法设计为何需要重新考虑

当前任务可写成三步：原句x → 规则y；公开场景G与规则y → 执行器决策d；最后评价d是否满足原句。

在Fair30的构造中，selection、availability_reference、return_by均由原句明确规定。距离、到达时间和营业窗口决定某个候选是否可行，却不决定用户到底要求哪个规则。例如场景不可行，也不能把“必须出发时开门”改成“到达时开门”。这使得计算事实对规则抽取的额外作用并不直接；它可能提示某种解释后果，但不能作为原句含义的正确性证明。

同时，原句含有“若无可行药房，报告INFEASIBLE”，system却要求模型只返回规则，并明确由执行器处理最终决策。看到事实表后模型更常直接求解，是与原始回复一致的解释，但尚未通过受控实验确证。

因此当前最合理的接口是：**保留任务约束，明确只由执行器报告最终对象和不可行性；模型只输出规则字段。** 直接规划是另一种任务，若以后采用，所有方法都应输出同一决策格式并使用新的公平评价，不能只给证据组开后门。

对EI论文目标的影响：把DSL定义讲清楚或去掉矛盾职责，本身不足以成为有说服力的方法贡献。“语言模型＋求解器”也不能直接当成新增贡献。暂不为当前实现改一个新名字继续扩量。

## 4. 可执行请求计划：2×2接口诊断

为了区分“事实复核无增益”和“事实表触发了输出职责混淆”，准备四个条件：

| 条件 | 原句职责表述 | 复核信息 |
|---|---|---|
| O-L | 原表述 | 原句、scene、Direct候选 |
| O-E | 原表述 | 同上＋计算事实 |
| C-L | 明确执行器负责最终决策 | 原句、scene、Direct候选 |
| C-E | 明确执行器负责最终决策 | 同上＋计算事实 |

仅替换原句中的一句，不改system、DSL定义、scene、gold、候选政策、事实计算、解析器或回退规则。

原句：
```text
If no pharmacy can satisfy every requirement, report INFEASIBLE.
```

澄清句：
```text
If no pharmacy can satisfy every requirement, the downstream executor reports INFEASIBLE. Your task is only to extract the requested rule fields; preserve those rules even when no pharmacy is feasible.
```

采用全部30个已批准案例，不只选那12条失败；固定每例原Fair30第一次Direct候选，四条件逐例完全共享。每条件每例一次，共 **120个计划请求**。旧候选故意保留，用来隔离复核输入变化；不把此设计称作新的端到端性能评估。四条件均须新采，同一轮交错执行，原表述条件不能直接复用历史回答。

四条件顺序按案例序号固定循环轮换，不按得分选择；30例不是4的整倍数，位置分配并非完全相等，应披露。使用既定Haiku/xcode、temperature0、输出1600、并发2；单元最多2次尝试，总恢复最多12次，总物理预算132。只重试传输失败，401/403/429及恢复耗尽停止。候选生成费用是历史共享成本，新增复核与历史候选成本分开披露。

**当前已完成请求生成和隔离性测试，尚未实现本诊断的真实采集与回放适配，也没有发起API调用。** 下一步若执行，应先完成120单元收集/审计适配及断网模拟，沿用原错误计分和版本冻结要求，不手工逐条调用替代账本。

## 5. 指标、验收与停止条件

主要诊断：证据组合同失败率的下降（O-E减C-E），同时比较语言组的相同变化（O-L减C-L），报告两者差值及逐例配对。两种原句长度不同，诊断的是“职责澄清这项文本干预”的效果，不能声称已隔离所有提示长度影响。

次要指标：固定分母的原始/回退后任务成功、规则正确、纠正和改坏、token、延迟、所有传输失败。30个案例四条件相互配对，不当作120个独立案例；这是暴露开发数据上的事后机制诊断，不据此宣称显著或SOTA。

- 若澄清降低合同失败，但C-E仍不优于C-L：确认接口问题值得修复，计算事实复核仍无额外收益，停止该机制扩量。
- 若澄清没有降低合同失败：职责冲突不足以解释主要现象，停止围绕该句反复调参。
- 若C-E出现正向净任务差：只获得后续研究线索；需检查是否依赖回退、少数案例或提示顺序，再决定是否投入新任务和外部数据，不能直接启动论文。

禁止修改旧Fair30评分、把非法决策反向补成规则、挑选“最难”案例重跑、因答错加重试，或把请求准备成功称为模型实验完成。
