# Luna API速度对比：FHL vs xcode

日期：2026-09-10。模型：`gpt-5.6-luna`。范围：开发测速，不是论文结果。

## 同时启动的真实提示测试

两边使用相同5条手工解析提示、HTTP/1.1、60秒单调用执行上限、零重试，同时启动，各自串行执行。遇首个供应商失败后停止。

| API | 已尝试 | 成功 | 成功响应延迟 | 失败 | 全部尝试平均延迟 |
|---|---:|---:|---|---|---:|
| FHL | 4 | 3 | 17.004、30.216、34.949秒；均值27.390秒 | HTTP 429 rate limit，7.521秒 | 22.423秒 |
| xcode | 2 | 1 | 42.761秒 | 60秒超时，60.012秒 | 51.387秒 |

在本轮可比较的成功响应中，FHL平均成功延迟比xcode唯一成功响应低15.371秒，约低35.9%；换一种表达，xcode约为FHL的1.56倍。样本很小且xcode只有一个成功响应，这只是本时段节点诊断，不能当成稳定服务等级。

## 相同简单JSON探针的辅助证据

HTTP/1.1、120秒配置下：

| API | 并发 | 结果 | 批次墙钟 |
|---|---:|---:|---:|
| FHL | 4 | 4/4 | 44.795秒 |
| xcode | 4 | 4/4 | 66.579秒 |

以批次完成吞吐计，FHL约为xcode的1.49倍。FHL继续提升到6路时只有4/6成功，因此4路是当前观察到的稳定并发上限。

## 判断

FHL在成功窗口内明显更快，约有1.5倍吞吐优势；xcode更慢，并出现60秒超时。FHL的主要风险是TLS波动和429上游限流，速度优势不等于稳定性优势。当前576单元Luna实验应优先保留FHL节点和最多4路并发，但只有在健康检查连续通过后恢复；节点持续429或TLS失败时继续并发不会更快。
