# Proposal v6（候选）：面向可执行本体的保守约束解析与后果校验

日期：2026-09-12。状态：候选研究方案，尚未进入确认性实验或论文写作。

## 0. 研究定位

本方案保留“设计一个机制，并证明特定指标提升”的目标，但更换机制对象：不再主张计算事实复核本身能普遍提升路线规划，而是研究自然语言约束进入可执行 ontology 时的忠实性、合同合规性与任务后果。

Travel 诊断提供了问题动机：DeepSeek 在 60 条唯一输入中基础字段稳定，但出现 `重庆美食`→官方 `川菜`、`历史人文`→官方 `历史古迹/人文景观` 的 ontology 不一致；Gemini 3 Flash 的合法输出子集未见更多语义错误，但 8/48 唯一响应违反字符串类型合同，另有传输/JSON 失败。上述结果是开发诊断，不是新方法收益证据。

## 1. 题目与核心问题

**中文题目**：面向可执行本体的保守约束解析：自然语言规划接口的语义忠实性与任务后果

**英文题目**：Conservative Ontology-Grounded Constraint Parsing for Executable Planning Interfaces

**核心研究问题**：一个显式的“证据—ontology—执行后果”解析机制，能否在不把模糊偏好强行具体化的前提下，同时提高 schema 合规率、语义忠实率和最终任务成功率？

这里的“提升”必须至少体现在一个预先指定的主指标上，并且不能以牺牲另一个主指标换取：不得只提高 JSON 合规率，却增加语义臆造或任务失败。

## 2. 机制：COG-Guard

COG-Guard（Conservative Ontology-Grounded Guard）由四个固定模块组成：

1. **字段证据抽取**：每个非空字段必须保留原句逐字证据；无证据只能输出 null/unsupported。
2. **ontology 候选映射**：自由文本偏好先进入官方枚举候选集，输出 `accepted`、`ambiguous` 或 `unsupported`，禁止把未确认的自然语言短语直接写入执行字段。
3. **保守决策门**：只有当证据片段与 ontology 候选满足预先冻结的映射规则时才接受；多个候选或只存在地域/风格暗示时保留歧义，不擅自选类别。
4. **后果校验**：仅对已接受字段编译执行约束；检查该字段是否改变可行性、候选选择或官方评分。后果只能用于发现需要复核的字段，不能反向制造用户偏好，也不能在评分阶段偷偷映射。

关键机制不是“多调用一次模型”，而是把自由文本、可执行 ontology 与后果验证分成有权限边界的层：语言证据决定是否可接受，ontology 决定能否执行，后果只决定是否需要人工/模型复核。

## 3. 对照与可否定假设

至少比较以下方法，保持相同模型、输入、后端与预算：

| 方法 | 机制 | 目的 |
|---|---|---|
| Direct | 直接输出完整字段 | 最低成本基线 |
| JSON-only | 仅 schema/类型约束 | 区分格式收益与语义收益 |
| Evidence-only | 字段必须带原句证据 | 区分证据约束收益 |
| Ontology-only | 枚举约束，无后果校验 | 检验 ontology 约束的独立作用 |
| COG-Guard | 证据 + ontology + 保守门 + 后果校验 | 主机制 |
| Oracle-upper-bound | 独立人工确认的 ontology 标签 | 只作为上限，不作模型方法 |

预先注册假设：

- H1：COG-Guard 提高 schema 合规率，且不增加语义臆造率。
- H2：COG-Guard 相比 JSON-only 提高语义忠实率，而不是只改变输出格式。
- H3：COG-Guard 相比 Ontology-only 减少把模糊自然语言强行映射为具体类别的错误。
- H4：只有当 ontology 错误会改变执行约束时，后果校验才提高最终任务成功；对无后果样本不应制造额外改动。

否定条件：主任务成功不提升、收益仅来自回退、收益只存在于 schema 合规率、或人工复核发现 COG-Guard 的 null/unsupported 率只是逃避解析，均不能称机制成立。

## 4. 数据与实验边界

第一阶段使用 Travel 的独立审核子集作为开发诊断，不称 benchmark。当前 60 条 dev 输入中，DeepSeek 100 次和 Gemini 100 次结果只能用于错误分类；不得把 40 次重复调用当作 40 个独立样本。

正式确认实验必须重新冻结一批未用于规则编写的输入，至少覆盖：明确枚举、地域/风格描述、模糊偏好、缺失字段、冲突字段、房型/交通方式和多字段组合。每条输入由两名审核者确认：原句证据、允许的 ontology 映射、是否应保留 unsupported，以及官方执行约束的覆盖关系。

模型输入只能包含原句、公开 ontology 定义和公开场景。人工标签、官方 hard_logic_py、评分结果和后果报告不得进入模型输入。gold 只在独立评分阶段使用。

## 5. 指标与分母

主指标按完整预注册分母报告：

- schema 合规率：缺失、额外键、类型错误、数组/字符串错误均失败；
- 证据忠实率：非空字段证据必须逐字来自原句；
- ontology 忠实率：接受的枚举必须得到人工审核支持；模糊项输出 null/unsupported 不算错误，但另报保守拒答率；
- 语义臆造率：原句未支持却输出具体值的比例；
- 官方任务成功率：包括 schema、解析、规划和官方 hard constraints 的完整链路；
- 后果敏感度：语义错误中实际改变可行性、选择或分数的比例；
- 纠正/改坏：相同初始候选上的成对统计；
- 传输、JSON、schema、语义、规划失败分层；不把回退成功隐藏为模型原始成功。

所有模型失败、超时、未完成和重试都保留在分母账本中。模型调用次数、token 与延迟单列，不以重复调用增加独立样本量。

## 6. 推进门槛

### Gate 0：机制合同

离线通过输入隔离、ontology 枚举、证据引用、null/unsupported、拒绝非法类型和篡改检测；无 API 调用。

### Gate 1：开发诊断

在独立审核的 20–30 条开发样本上，COG-Guard 相比 Direct/JSON-only 同时满足：schema 合规率提高至少 10 个百分点，语义臆造不增加，且至少出现 3 条可人工确认的 ontology 错误纠正。否则修改机制或停止，不扩量。

### Gate 2：机制对照

在未参与规则设计的新开发簇上，COG-Guard 相比最强简单基线在 ontology 忠实率或官方任务成功率上有预先定义的绝对提升，且不是由回退或删字段造成；若只有格式改善，研究结论降级为接口工程报告。

### Gate 3：确认实验

只有 Gate 2 通过，才冻结测试集并执行跨模型确认。主张必须同时报告语义指标和任务指标；若两者不一致，按不一致结果解释，不选择性报告较高者。

## 7. 与旧主实验及 Travel 的关系

- 旧 DARC-Route 的“决策对比证据复核”保留为历史对照，不再作为 v6 主机制。
- Travel 的 DeepSeek/Gemini 结果是机制动机和错误 taxonomy，不是确认性正结果。
- 不把弱模型的格式失败包装为架构收益；弱模型只用于压力测试，强模型也必须接受同一合同。
- 不启动旧主实验的完整测试扩量，直到 COG-Guard 在 Gate 1/2 显示独立净收益。

## 8. 最小执行顺序

1. 冻结 ontology 词表、证据合同、unsupported 规则和完整分母账本。
2. 在不看模型输赢的前提下审核新的 20–30 条开发簇。
3. 实现 Direct、JSON-only、Evidence-only、Ontology-only、COG-Guard 五个离线/在线接口。
4. 先做无模型回放和篡改审计，再用一个主模型完成 Gate 1。
5. 若 Gate 1 通过，再用第二模型做机制迁移诊断；若失败，停止调参并重新评估 proposal。
6. Gate 2 通过后才写确认实验计划；论文继续 CLOSED，直到独立验收。

## 9. 当前不允许的做法

- 不把 `重庆美食` 自动改成 `川菜` 后重新评分；映射必须在模型输出阶段显式发生并可审计。
- 不把 `历史人文` 静默替换为 `人文景观`。
- 不把数组字符串自动压平后计为 schema 正确。
- 不从 hold 集临时挑选最容易暴露错误的样本。
- 不因弱模型错误就宣称 COG-Guard 有效；必须与同模型基线比较。
- 不在 Gate 失败后通过新增模型、重复调用或更换指标延长实验。

## 10. 当前结论

建议从旧 proposal v5.1 转入 v6 候选，但暂不宣称创新已成立。v6 的可发表性取决于一个具体、可否定的结果：在同一原句和同一执行后端下，显式证据—ontology—后果权限边界是否能带来独立于 JSON 格式修复的语义与任务提升。
