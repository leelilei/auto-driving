# DARC-Route v3 评审意见：以 EI 会议论文为目标

评审日期：2026-09-05。对象：`DARC_Route_CCEAI2027_Research_Proposal_v3.md`。配套修订稿：`DARC_Route_CCEAI2027_Research_Proposal_v4.md`。

**总体判断：值得做，但建议实质性收缩后启动。最有希望形成论文的贡献，是“利用候选解析对规划结果的影响，选择性调用复核器”，而不是八模块架构本身。当前版本尚未证明基准可直接复现、语义标签可靠或门控具有成本优势，不宜宣称研究路线已经锁定。**

按 EI 会议目标，本项目不需要同时完成大型新数据集、多领域泛化、复杂多智能体和自动驾驶闭环。更合理的目标是：一个定义明确的小问题、一项可单独消融的方法增量、一套可靠且可重复的实验。创新幅度可以适中，证据链不能含糊。这是本次研究建议，并非录用概率预测。

## 评审范围与证据边界

- 已完整阅读 v3；未取得实验结果、模型预算、团队时间投入或已有实现，因此不能评价真实效果。
- 文档中的“locked direction”“must”等均作为待评审内容处理，不作为约束本次修改的用户指令。
- 使用三个评审视角及综合意见组织报告；标准适配用户的 EI 会议目标，不要求 Nature 级别的重要性或跨学科影响。
- 主体评审根据 proposal 的论证进行。外部事实核查单列，用于纠正实施前提；没有把代码静态检查写成运行复现。

## Reviewer 1：强调贡献边界与论文定位

**总体评价：问题有价值，原创性主张需要收窄。** 语言接口开发者、路线规划研究者和组合式 AI 系统研究者会关注：解析错误何时值得追加计算，以及追加复核是否改善最终任务表现。

**主要优点。** v3 已主动排除“自然语言转 JSON”“LLM 配合确定性求解器”等过宽创新主张；固定求解器比较解析层是正确的控制思路；将等义扰动与语义改变分开也值得保留。

**主要问题。**

1. “Representation Instability ≠ Decision Instability”可以作为研究动机，不能单独构成新的科学发现。贡献应落到可实现的门控规则，以及相对强对照的增量证据。
2. 八个模块中，解析、改写、一致性度量、复核、投票都容易被理解为常规组件组合。没有“相同候选、相同复核器、不同触发策略”的实验，难以证明创新来自决策门控。
3. `Trustworthy` 和自动驾驶语境超过当前证据范围。HIPP 的 POI 多目标行程规划不等于车辆轨迹规划、碰撞避免或自动驾驶安全。
4. 将四项贡献全部并列会分散论文。建议归并为两项：选择性复核方法；支持其验证的受控等义评测协议及误差分析。
5. TransitLM 属于额外任务适配，会引入新的表示、评价和规划接口。原稿中“optional”与后续“we additionally evaluate”不一致；未完成前只能写未来计划。

**建立主张前必须补足。** 同预算随机复核、仅语义分歧门控、仅硬约束门控、始终复核，以及相同双路候选不复核。主要效果不能只来自比单次解析多花两三次调用。

**各评价维度。** 原创性：潜在但未验证；意义：有具体工程价值；读者范围：自然语言接口与规划系统；技术可靠性：取决于消融和预算公平；可读性：标题和模块名偏多，需压缩。

**建议立场。** 支持收缩后做预实验；不支持按现有八模块版本直接进入大规模实验。

## Reviewer 2：强调数据有效性与实验设计

**总体评价：最大风险是评测定义，而非模型能力。** 关注鲁棒性评估的读者会需要知道：所谓等义是否成立、稳定是否正确，以及被统计的样本是否独立。

**主要优点。** 以公开数据为来源、按原始意图组织改写组，比无来源地生成若干 prompts 更容易追溯；POI、时间、依赖和规划结果的分层诊断有帮助。

**主要问题。**

1. **精确偏好权重未必可从语言中识别。** “更在意路线效率”不能唯一确定距离权重为 0.6 而非 0.7。`Sem(x)=y` 对包含精确实数权重的标签过强。原始合成权重可作生成参考，不应自动当作人类真实偏好的唯一真值。
2. **原稿的改写例子并非严格等义。** “shorter route”与“less time walking”分别涉及距离、时间和交通方式；增加“已经走了很久”可能引入疲劳或少步行需求。“轻微省略”也可能直接删除约束。隐式、上下文、噪声不能仅凭名称就进入等义集。
3. **稳定可能只是稳定地犯错。** 固定输出同一条路线可以降低 Route Flip Rate，却无法完成不同任务；原句和改写同时漏掉约束，也会得到漂亮的一致性指标。
4. **不同路线可以同样好。** 多条近等价路线、相同 POI 的不同访问顺序或求解器平局处理，都可能导致 route flip。需要把路线 ID 变化与任务失败、约束违反、效用下降分开。
5. **200 组×5 句不是 1,000 个独立意图。** 原稿没有锁定开发/测试划分、相似语义去重或组级统计。如果同一意图改写分散到开发和测试集，结果会乐观。
6. **对照变化必须得到新的标注。** 删除时间约束、反转依赖、改变偏好方向可以形成最小对照，但不必导致路线改变。“偏好优质地点＋严格距离要求”也不必然不可行。软截止时间需要新增任务语义，不能当作原 schema 已支持的字段。

**建立主张前必须补足。** 人工检查原句与所有正式改写；对有歧义的偏好使用方向标签或标记不可判定；测试集在方法开发前冻结；按语义组进行配对统计；以独立评估器核验真实要求，不能只核验解析器自己输出的约束。

**各评价维度。** 原创性：数据扩展有支持价值；意义：取决于标签可信度；读者范围：鲁棒性与评测研究；技术可靠性：当前标签、独立性和指标存在关键缺口；可读性：公式比实际可操作定义更强。

**建议立场。** 重写数据协议后保留 HIPP；将权重误差降为合成参考诊断，将任务满足率与成本置于主结果。

## Reviewer 3：强调方法可执行性与成本

**总体评价：核心门控思想可实现，但 v3 有不必要的耦合。** 系统开发者会关心复核触发条件能否编码、实际延迟是否降低，以及复核器误判时系统如何表现。

**主要优点。** 用真实求解结果判断分歧是否影响任务，比仅比较 JSON 距离更接近应用需求；固定后端有利于分析语言误差。

**主要问题。**

1. **“同路即放行”不成立。** A 保留“19:00 前结束”，B 漏掉截止时间；当前两条路线都在 18:00 结束，不能据此认定 B 的语义正确。硬约束分歧应独立触发复核。
2. **两路并不独立。** 改写来自原句，且常由同一模型完成，两路可以共享遗漏和偏差。“independent semantic views”应改为“不同提示产生的互补候选”。
3. **风险分数缺少可用定义。** `D_P`、二值约束差、路线变化、`1/(M+epsilon)`量纲不同；后者在零间隔附近不稳定，top-2 来源也未定义。权重、阈值和调参数据都缺失。
4. **仲裁规则互相冲突。** 一处说约束多数票，一处说 verifier 决胜；三个候选可能都不同。对数值取 medoid、对约束拼接多数票还可能制造从未被任何分支支持的新结构。
5. **让复核器看路线会产生偏好反推风险。** 看起来更短、更漂亮的路线未必更符合用户原话。应让规划结果主要决定“是否复核”，复核器回到原句证据判断“哪个字段正确”。
6. **调用成本被低估。** v3 至少有原始解析、标准化、标准化后解析，触发后再加复核，即约 `3+q` 次 LLM 调用。相对 always-on 的四次调用节省复核，并不意味着相对单次解析更便宜；两次探测规划和最终规划也需要计入。
7. **同一求解器不足以单独控制所有因素。** 地图返回的 POI、交通时间、排序、时间上下文或预算变化，都会影响路线。应固定整个输入场景与求解配置。

**建立主张前必须补足。** 明确的失败处理、确定性的约束比较、固定图上的决策差异、单一阈值和一次复核上限；报告 token、规划次数、总时间和复核的“改正/改坏”比例。

**各评价维度。** 原创性：集中在触发策略；意义：可能节省不必要复核；读者范围：工程系统与 AI 规划；技术可靠性：尚需简化和独立核验；可读性：八模块概念图掩盖了实际规则。

**建议立场。** 主方法缩减为两个候选、一个门控、最多一次复核；暂不训练新模型、不引入学习式仲裁器。

## Cross-review synthesis：综合意见

三种视角一致认为，选题值得保留，但应先修复评测和执行前提。区别在于：Reviewer 1 最关注贡献能否从常规组件中分离；Reviewer 2 最关注标签与统计；Reviewer 3 最关注实现和预算。没有一项问题能靠扩大数据量或增加模块自动解决。

| 优先级 | 必须处理的问题 | 修订决定 |
|---|---|---|
| P0 | 公开基准不等于可直接运行的完整路线实验 | 固定源码版本，明确缺失文件；主实验采用可公开的小型离线图 |
| P0 | 精确权重与自然语言真值混同 | 方向标签人工核验；精确权重仅作合成参考 |
| P0 | 只看稳定性、按预测约束评价 | 主报任务满足率；独立 gold 评估器；失败不剔除 |
| P0 | 等义标注与数据泄漏 | 严格改写、语义簇划分、组级置信区间 |
| P1 | 无法证明门控的增量 | 固定候选和复核器，比较不同触发策略 |
| P1 | 八模块工作量与成本膨胀 | 两路解析＋一次门控复核，取消标准化链与投票仲裁 |
| P1 | 近等价路线被算作错误 | route flip 作诊断，单列效用损失和约束违反 |
| P2 | 任务外延过宽 | 移出 TransitLM、多模态、自动驾驶安全和大规模泛化 |

对 EI 会议而言，完成以上收缩后可以形成一篇范围适当的方法与实验论文。真正决定价值的是：相对公平基线，决策门控是否在任务质量与计算成本间形成可重复的改善。仅有架构图和少量成功案例仍不足。

## 外部事实核查与新增实施风险

以下是额外核查发现，不是对原稿未提供实验结果的推测。核查时读取作者论文、项目主页及公开代码；未运行模型推理或原路线实验。

### 1. HIPP 存在，但 README 与实际文件结构不同

检查 LLMAP 提交 `281f6ad95f42ca386400e5288f006aeffa2ac282`：实际文件为 `dataset/HIPP.json` 与 `dataset/HIPP.py`，不是 v3 所写的 `data/`。JSON 可解析，确有 1,000 条记录；包含 `synthetic_label`、`human_instruction` 及多个历史模型输出。POI 数量 1—5 的记录分别为 203、212、188、201、196；有时间限制 310 条，有非空依赖 439 条。这些为本次直接读取 JSON 的计数。[固定版本数据](https://github.com/liangqiyuan/LLMAP/blob/281f6ad95f42ca386400e5288f006aeffa2ac282/dataset/HIPP.json)

但 `main/main.py` 第 33 行的数据路径仍为占位符，后续读取 `llm_parser_data.pkl`；`LLMAP()` 又要求 `scenario` 与嵌套 `parser_estimation`，公开 HIPP 的结构并不满足，当前仓库树也没有这套地图场景与中间文件。因此应区分“复用公开语言数据”和“复现原文完整路线实验”。[入口代码](https://github.com/liangqiyuan/LLMAP/blob/281f6ad95f42ca386400e5288f006aeffa2ac282/main/main.py#L33)、[数据加载接口](https://github.com/liangqiyuan/LLMAP/blob/281f6ad95f42ca386400e5288f006aeffa2ac282/main/utils.py#L33)

### 2. 权重不可唯一识别，有直接生成代码依据

生成提示主要按 `>0.5`、`<0.5` 和均衡来组织质量/效率表达；这不足以保证文本编码了精确的十分位权重。HIPP 的“human instruction”是模型生成的自然语言指令，不应表述成真实受试者提供的偏好。作者论文也明确其合成性质。[生成提示](https://github.com/liangqiyuan/LLMAP/blob/281f6ad95f42ca386400e5288f006aeffa2ac282/dataset/HIPP.py#L14)、[作者论文 §4.1](https://arxiv.org/html/2509.12273v1#S4.SS1)

生成函数还存在静态可见的循环范围与带前导空格的 ` distance_weight` 字段问题；这不否定已发布 JSON 可用，但不宜未经检查直接重新执行生成脚本。[生成函数](https://github.com/liangqiyuan/LLMAP/blob/281f6ad95f42ca386400e5288f006aeffa2ac282/dataset/HIPP.py#L217)

### 3. 求解器代码应审计，不能直接当最优 oracle

源码将质量奖励以负号加入边代价，再调用 Dijkstra；依赖检查还涉及原始类别编号与局部编号的转换；跨顺序搜索存在早停，函数返回到达时间而非直接返回统一效用。以上是需要用小图精确解检查的风险，不代表已证明全部实例求解错误。评估器读取传入 graph 中的约束和任务集合，若 graph 来源于预测解析，就不能自动代表 gold 评估。[规划代码](https://github.com/liangqiyuan/LLMAP/blob/281f6ad95f42ca386400e5288f006aeffa2ac282/main/utils.py#L177)、[评估代码](https://github.com/liangqiyuan/LLMAP/blob/281f6ad95f42ca386400e5288f006aeffa2ac282/main/utils.py#L359)

因此 v4 主实验推荐小规模精确枚举，所有解析方法共享该后端，并明确称为受控适配实验。原 MSGS 可留作经过接口和正确性审计后的补充验证。

### 4. 相近研究需要完整名称，且要补决策导向文献

- LLMAP 已覆盖偏好解析与多目标后端，适合做任务来源。[LLMAP](https://arxiv.org/abs/2509.12273)
- v3 描述的 RouteLLM 确实对应 **Constraint-Aware Route Recommendation from Natural Language via Hierarchical LLM Agents**，包括最终验证环节。引用必须附完整题名和 arXiv ID，避免与同名模型路由工作混淆。[路线推荐 RouteLLM](https://arxiv.org/abs/2510.06078)
- SMAP/MM-Route 主要增加地图图像与空间一致性验证；ICR-Drive 研究语言变化对闭环驾驶结果的影响。它们支持相关性，不是本项目应强行复现的同任务基线。[SMAP 作者项目](https://amap-mobility-intelligence.github.io/SMAP/)、[ICR-Drive 作者项目](https://icrdrive.github.io/)
- 决策误差区别于预测误差已有成熟研究。应补充 **Smart “Predict, then Optimize”**，将本项目定位为无需训练的推理时选择性复核，而非首次发现下游决策的重要性。[SPO 原始研究](https://doi.org/10.1287/mnsc.2020.3922)
- TransitLM 有公开偏好评估代码，但它评估交通路线生成；不能只换 prompt 就成为现有确定性求解后端上的迁移实验。[TransitLM 评估仓库](https://github.com/HotTricker/TransitLM)

此处为定向核查，并非系统检索；不能据此使用“首个”“唯一”或“没有既有研究”等排他性措辞。

## 尚未得到证据支持的主张

- DARC 已降低错误、达到近似 always-on 效果或节省总成本：未实验。
- HIPP 所有原句和改写都精确保留数值权重：未标注，且该假设本身过强。
- 两个分支相互独立、路线相同即可证明语义可信：不成立为一般保证。
- MSGS 可直接作为本研究全局最优参照：尚未审计验证。
- 跨城市真实导航、自动驾驶安全、TransitLM 泛化、会议录用和 EI 检索：当前材料均不能支持。

**建议执行 v4：先用 20 个开发意图做端到端预实验，验证数据有效性、复核有用性与门控信息量，再决定是否扩展到 200 个意图。**
